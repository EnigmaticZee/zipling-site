How it works

Most archivers squeeze bytes.
Zipling reads the file first.

Three parts of Zipling's engine are its own, built from scratch and measured against the best there is. The rest is proven parts, chosen because the numbers said so. Every figure here comes from the published benchmarks, with every archive extracted and compared byte for byte.

What is ours

Three things no other archiver has.

  1. 1

    A JPEG coder that beats the best there is.

    A photo is already compressed, so a zip saves almost nothing on it. Zipling takes the numbers inside the JPEG apart and codes them with a coder of its own. It is smaller than Lepton, the coder Dropbox and Microsoft built for exactly this job and the best published one, and it decodes three and a half times faster. It also sees something no other JPEG coder models: in a typical photo, more than half of the 8-by-8 blocks repeat an earlier block exactly, and Zipling stores those as a reference. The photo comes back bit for bit, and Zipling proves that before it keeps the smaller form.

    2.5%smaller than Lepton on the same 382 photos
    3.5×faster to decode than Lepton
    27%off the photos: 94.7 MB to 69.0 MB
    388 of 388test photos back bit for bit

    Measured against Lepton 0.5.8 on 382 baseline photos, one thread each. Zipling keeps Lepton as a fallback for progressive JPEGs and the few photos where it does better.

  2. 2

    A pixel coder for screenshots and graphics.

    A PNG or a PDF hides old, weak compression inside. Zipling undoes it exactly, and that alone makes screenshots and PDFs 56% smaller than a zip. At the Max setting it goes further: its own pixel coder predicts each pixel from its neighbours and stores only the difference, 19% smaller than xz, the strongest general-purpose compressor, on the same pixels, and faster to decode. It is chosen image by image. Flat screenshots do as well with the general codec, so they stay there.

    56%smaller than Finder's zip on PDFs and screenshots
    19%smaller than xz at its best, on photo-like PNGs
    100 MB/sto decode, on one core
    Every pixelback exactly, and the PNG file with it

    Measured against xz -9 on 439 PNGs. No other archiver codes pixels; they compress the PNG file as it is.

  3. 3

    Archives that repair themselves, even when bytes have moved.

    Tick one box and a Zipling archive carries its own repair data, 3% of its size unless you choose more. If a disk fails or a download breaks, Zipling finds the damaged slices by their checksums and rebuilds them exactly, even when the end of the file is missing. It also handles what most repair schemes cannot: bytes inserted or dropped in the middle. Every slice carries an anchor, so a slice that has shifted is found again and the file is brought back to its original layout. Damage beyond the budget is reported, not guessed: Zipling names the files that are lost.

    3%of the archive repairs any 3% of damage, anywhere in it
    1 to 50%your choice, for the files that matter
    49 sto repair six damaged regions and a lost footer in a 17 GB archive, byte for byte
    0 sadded to extraction: the record is read only when something fails

    The only Mac archiver with repair data inside the archive; the one peer anywhere is WinRAR's recovery record. ZIP and 7z get a small recovery file beside them instead.

Proven parts, chosen by the numbers

The rest is well-known ideas, done properly.

None of these is new on its own. No Mac archiver puts them together, and each earned its place in a benchmark.

It reads the file first.

Every file is identified by its bytes, never its name, and goes to a lane with the compressor that suits it: text, code, binaries, images, media that is already as small as it gets. Six lanes, each with its own codec.

It keeps one copy of repeated data.

Identical files, and identical pieces of big files, however far apart, are stored once. A backup with old copies gains a lot; a folder with nothing repeated gains nothing.

It lines up app code.

A Mac app is mostly machine code. Zipling rewrites the jumps inside it so repeats line up: 35% smaller than Finder's zip on eight Mac apps, 9% smaller than 7-Zip's best in less than half the time.

It uses every core, all the time.

Files stream into independent blocks that every core compresses at once, and extraction works the same way. A 736 MB folder is packed in 0.5 s at Fast and 9 s at the default setting. Finder takes 24 s.

It picks the right codec for each lane.

zstd where speed matters, LZMA where size does, and a BWT coder (libbsc) on text and code at Max, where it is 20% smaller than LZMA on text and 16 times faster to compress.

It checks everything, twice.

Every block carries a keyed checksum and the index a BLAKE3 hash, verified while the archive is written and again while it is extracted. Every transform above is proved by rebuilding the original before the smaller form is kept.

Where it is still behind

Not everything, not yet.

The same benchmarks that show the wins show these. Nothing on this page is hidden from them.

Data with nothing to read

On the standard Silesia corpus, generic data with no file types to exploit, the default setting is 16% bigger than 7-Zip's default (57.3 MB against 49.6 MB). Max is 4% smaller than 7-Zip's best, and eight times faster, but the default is built for real folders, not for this.

Source code at the default setting

On 89 Rust crates the default is 3% bigger than 7-Zip's default (9.5 MB against 9.2 MB), in a seventh of the time. Max matches the best of xz at 8.3 MB.

Photos that are not JPEGs

The JPEG coder is for JPEGs. HEIC photos from an iPhone, and videos, are already as small as they get and are stored as they are.

The pixel coder at the default setting

It runs at Max only, which keeps the default setting's extraction quick. Unpacking the PNG alone already makes screenshots 56% smaller than a zip there.

A password on Zipling archives

Not yet; it is planned. For anything private today, choose ZIP or 7z, which Zipling locks with AES-256.

Intel Macs

Zipling runs on Apple silicon today. An Intel build is planned, and the code filter for Intel apps with it; a universal app gets only its Apple silicon half lined up for now.

RAR

Zipling opens RAR archives, including locked ones, but does not create them. RAR is proprietary; convert one to a Zipling archive or a zip instead.

Ultra*

An experimental setting in the engine squeezes 0 to 3% more than Max for up to twice the time. It is not in the app and will not be until it earns its place.

Numbers move

Times vary about 10% between runs, and the default setting's archive size varies by up to 0.3% because blocks are cut by whichever core gets there first. The files inside never vary.
